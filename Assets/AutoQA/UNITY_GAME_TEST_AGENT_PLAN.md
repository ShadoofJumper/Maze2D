# План реалізації модульного агента для тестування Unity-гри

Дата: 2026-11-16. Статус: узгоджена архітектурна основа для реалізації через Codex у Rider.

## 1. Мета та зафіксовані рішення

Створити систему, яка отримує структурований стан Unity-гри, обирає наступну дію, виконує її та перевіряє результат. Механізм вибору дій має замінюватися без змін у Unity-інтеграції.

Перша ітерація:

- Запущена гра в **Play Mode всередині Unity Editor**, без створення білда.
- Доступ до Editor через **Unity CLI та Unity Pipeline**.
- Агент і Test Runner працюють локально, поза Unity.
- Провайдер рішень — **Ollaya**, яка вже встановлена та доступна локально. Це назва, надана власником проєкту; не підміняти її Ollama.
- Ollaya використовується в ролі селектора дій типу JEV/System One. Окремого LLM-планувальника в першій ітерації немає.
- Основне джерело спостережень — структуровані дані Unity. Vision і аналіз скриншотів не потрібні для MVP.
- Перша реалізація виконує дії напряму через підтримувані обробники. Симуляція введення передбачена архітектурою як окремий режим.
- Граф переходів і журнал будуються незалежно від обраної стратегії.

Майбутній напрям: той самий Runtime-пакет працює у development-білді, зокрема на девайсі, через мережевий адаптер без CLI.

## 2. Межі MVP

Перший наскрізний сценарій: Main Menu → створення лобі → заповнення параметрів → запуск → підтвердження очікуваного стану. Якщо такої механіки немає, вибрати наявний еквівалент із кнопкою, зміною параметра та перевірюваним завершенням.

Почати з однієї UI-технології, яка реально використовується у проєкті. Не реалізовувати одночасно uGUI/TMP та UI Toolkit. Мінімальний набір інтеракцій визначає сценарій: активація кнопки, введення тестового значення, вибір опції; toggle — за потреби.

Не входять до MVP: універсальне проходження довільної гри, довільна генерація тексту, real-time керування персонажем, vision, LLM-планувальник, хмарне розгортання, повна підтримка всіх UI-контролів, відновлення довільного snapshot гри.

## 3. Архітектура та залежності

```text
Локальний Agent Host
  Test Runner
    ├─ Decision Policy: Ollaya / Random / Graph Exploration
    ├─ Trace Store + Transition Graph
    └─ Game Connection
         └─ Unity CLI Adapter
              └─ Unity Pipeline + наші Editor-команди
                   └─ Unity Runtime Core
                        ├─ Observation Collector
                        ├─ Action Catalog + Target Registry
                        ├─ Action Executor
                        ├─ Readiness / Session Lifecycle
                        └─ Game-specific Providers
```

### Unity Runtime Core

- Збирає спостереження та перелік доступних дій.
- Зберігає відповідність ID до живих Unity-об'єктів.
- Перевіряє та виконує команди на головному потоці Unity.
- Надає стан готовності, результати перевірок і lifecycle сесії.
- Не залежить від Unity CLI, UnityEditor, Ollaya або формату API конкретної моделі.

### Unity Editor / CLI Adapter

- Реєструє невеликий набір власних команд через підтримуваний механізм Unity Pipeline.
- Делегує роботу Runtime Core.
- Керує входом/виходом із Play Mode та виявляє втрату сесії після reload.
- Містить усі залежності від UnityEditor і Pipeline, потрібні лише для Editor.

### Agent Host

- Test Runner володіє циклом тестування; модель лише пропонує дію.
- Game Connection приховує спосіб доступу до гри.
- Decision Policy приховує спосіб вибору дій.
- Ollaya Adapter перетворює внутрішній запит на фактичний локальний протокол Ollaya.
- Журнал і граф доступні для всіх стратегій.

Для майбутнього білда додається Runtime Network Adapter до тих самих операцій ядра. CLI не має бути необхідним для компіляції чи роботи Runtime Core.

## 4. Основні абстракції

Наведені назви — проєктні поняття, а не готові API Unity або Ollaya. Остаточні інтерфейси визначити після огляду репозиторію.

| Абстракція | Відповідальність |
|---|---|
| Observation Collector | Узгоджений знімок сцени, UI, контексту, доступних дій |
| Game Context Provider | Специфічні правила, стан і прогрес гри |
| Interaction Provider | Виявлення елементів і побудова дій для певної UI-системи або gameplay |
| Target Registry | Відповідність ID елементів до живих об'єктів у поточній сесії |
| Action Executor | Валідація та виконання підтримуваних команд |
| Readiness Provider | Чи завершився перехід і чи можна виконувати наступну дію |
| Session Controller | Початок, reset, зупинка та стан тестової сесії |
| Test Oracle | Об'єктивні умови успіху, провалу та інваріанти |
| Game Connection | Спільний контракт доступу через CLI або майбутню мережу |
| Decision Policy | Вибір дії зі спільного набору кандидатів |
| State Identity Provider | Стабільна ідентичність стану для графа |
| Trace Store | Послідовність спостережень, рішень, дій та результатів |

Не перетворювати кожну абстракцію на окремий сервіс або пакет. Розділення потрібне для заміни реалізацій, а не для збільшення кількості компонентів.

## 5. Контракти даних

Серіалізовані контракти мають бути версіоновані, незалежні від Unity-об'єктів і API моделі. Достатньо JSON для MVP. Не серіалізувати всю сцену, довільні компоненти або внутрішні поля через reflection.

### Observation

- `schemaVersion`, `sessionId`, `observationId`, монотонна `revision` у межах сесії.
- Поточна сцена, активний екран/попап, якщо їх можна надійно визначити.
- `readiness`: ready / busy / unavailable і пояснення.
- Скорочена ієрархія та значущі тексти.
- Елементи UI: ID, тип, label/placeholder, поточне значення, активність, доступність; за потреби bounds та причина блокування.
- `gameContext`: JSON-сумісні специфічні дані гри.
- `availableActions`: конкретні допустимі кандидати.
- Результати oracle та діагностика.

Повну ієрархію залишати діагностичним артефактом. До Ollaya передавати компактну проєкцію спостереження з обмеженням обсягу. Не відкидати важливі причини недоступності дій заради скорочення.

### Action Candidate

- `actionId`, `targetId`, `kind`, зрозумілий опис.
- Конкретні параметри дії, спосіб виконання та передумови.
- Приклади: активувати Play; встановити difficulty=Hard; заповнити lobbyName тестовим валідним значенням.

Елемент і дія — різні сутності. Один dropdown породжує кілька кандидатів. Неактивний елемент можна включити до контексту, але не до переліку виконуваних дій.

Для MVP значення текстових полів беруться з конфігурованих fixtures/провайдера тестових даних. Модель обирає вже сформованого кандидата. Вона не повинна вигадувати методи, ID, параметри або C# код.

### Decision Request / Decision Result

Запит містить ціль тесту, компактне спостереження, доступні кандидати та обмежену історію останніх переходів. Відповідь містить обраний `actionId` або явну відмову/відсутність рішення. Оцінки кандидатів і confidence зберігаються лише якщо фактичний API їх повертає.

Внутрішній контракт не копіює схему Ollaya. Валідація відповіді обов'язкова: actionId має належати саме набору кандидатів цього запиту.

### Action Command

- `commandId`, `sessionId`, `observationId` / очікувана revision.
- `actionId`, execution mode, часовий ліміт.
- Параметри беруться з валідованого каталогу кандидатів, а не з довільного тексту відповіді моделі.

### Action Result

- `commandId`, статус: completed / rejected / failed / timedOut / unknown.
- Машинний код причини та короткий опис.
- Час виконання, фактичний execution mode, діагностика.
- Посилання на наступне спостереження або ознака, що його ще потрібно отримати.

`completed` означає завершення операції, а не успіх тесту. Успіх встановлює Test Oracle за станом гри.

## 6. Ідентичність та узгодженість

- Runtime ID унікальні в межах сесії; не покладатися лише на текст кнопки чи hierarchy path.
- Для replay між сесіями потрібен окремий стабільний semantic key або locator з однозначним зіставленням. Unity InstanceID для цього недостатньо.
- У простому MVP відхиляти команди за застарілою revision і отримувати новий знімок.
- ID знімка не змінюється від самого повторного читання; revision змінюється при релевантних змінах стану. Окремий capture ID допустимий.
- Один активний mutating command на сесію.
- Повторний commandId не повинен повторно виконувати дію. Результати зберігаються принаймні протягом сесії.
- Після втрати відповіді спочатку запитати статус команди. Якщо результат невідомий, зафіксувати невизначеність і переоцінити стан; не робити сліпий повтор кліку.
- Після domain reload або перезапуску Play Mode створювати нову сесію та інвалідувати старі ID.

## 7. Інтеграція з Ollaya

Ollaya вже встановлена. Не починати реалізацію з перевстановлення, зміни моделей або глобальної конфігурації.

Перед написанням адаптера виконати коротку read-only перевірку реального середовища:

1. Знайти доступний executable, версію та локальну довідку.
2. Визначити фактичну модель, спосіб запуску й підтримуваний API: HTTP або CLI.
3. Знайти наявні успішні запити/конфігурацію, якщо вони є у проєкті або надані власником.
4. Перевірити один мінімальний запит із кількома діями та структуровану відповідь.
5. Підтвердити, чи підтримується choice, як задаються варіанти та що саме означають числові поля відповіді.

Не переносити неперевірені назви endpoint, порти, CLI-прапорці чи JSON-схеми зі старого обговорення. Зокрема, не припускати сумісність Ollaya з Ollama або хмарним JEV API.

Після перевірки:

- Зберегти base URL / executable, назву моделі, timeout та ліміти в конфігурації Agent Host.
- Якщо є придатний HTTP API, використовувати його; інакше ізолювати виклик CLI всередині адаптера.
- Додати тайм-аут, обробку недоступності та валідацію відповіді.
- Записувати версію адаптера/моделі та параметри запиту для відтворюваності.
- При недоступності моделі завершувати запуск з явною причиною. Автоматичний fallback на іншу Policy дозволений лише якщо він заданий конфігурацією та відображений у звіті.

Мета запиту для MVP: обрати одну доступну дію, що просуває до заданої цілі, з урахуванням поточного стану й недавніх повторів. Універсальний запит не є гарантією довгострокового планування.

## 8. Виконання та очікування

Direct Executor виконує лише зареєстровані види дій. Навіть прямий режим має перевіряти активність і доступність цілі; не використовувати обхід блокувань як прихований спосіб досягти успіху.

Майбутній Input Executor реалізує ту саму семантичну команду через введення. Він може відмовити, якщо елемент перекритий або недосяжний. Способи виконання мають явно відрізнятися у звіті: прямий виклик не перевіряє реальну клікабельність UI.

Готовність гри визначається окремо від завершення команди. Для MVP використати явний readiness-сигнал від інтеграції гри та граничний timeout. Не вважати один фіксований sleep універсальним рішенням. Якщо застосовується стабільність UI, вона є евристикою та не замінює сигнал завершення завантаження.

Порожній список дій у busy-стані не означає провал. Порожній список у ready-стані потребує перевірки terminal state або фіксації блокування.

## 9. Test Runner та перевірки

Цикл:

1. Підключитися, узгодити версію контрактів і можливості середовища.
2. Почати сесію або виконати визначений reset.
3. Дочекатися ready в межах тайм-ауту.
4. Отримати observation.
5. Перевірити terminal conditions, інваріанти, exceptions і бюджети.
6. Передати стан до Decision Policy.
7. Перевірити рішення та виконати команду.
8. Отримати результат, дочекатися готовності, зібрати наступний стан.
9. Записати перехід у trace і граф; повторити.

Обмеження запуску: максимальна кількість кроків, загальний час, час рішення моделі, час дії, час очікування ready, межа повторів без прогресу. Вичерпання бюджету — окремий результат, а не автоматичний доказ бага гри.

Test Oracle задає об'єктивні умови: наприклад, гра перейшла в Gameplay і сесія лобі створена. Модель не є єдиним джерелом pass/fail.

Журнал має дозволяти відрізнити проблему гри, збій інтеграції, помилку моделі та невиконану передумову тесту. Останні Unity errors/exceptions збираються з обмеженням обсягу.

## 10. Граф і взаємозамінні боти

Transition Recorder отримує кожен підтверджений перехід незалежно від Policy. Вузол — абстрактний стан; ребро — дія, execution mode, результат і спостережений наступний стан.

State Identity Provider враховує екран/попап, значущі UI-значення та релевантний game state. Виключає час, анімацію, випадкові технічні ID та інші несуттєві зміни. Повний JSON hash не використовувати як універсальну ідентичність.

Graph Exploration Policy:

- Вибирає недосліджені дії поточного вузла.
- Зберігає фактичні переходи, включно з кількома можливими результатами однієї дії.
- Для повернення використовує відомий шлях або reset і replay, якщо це підтримується сценарієм.
- Обмежує повтори та не обіцяє повноту покриття довільної гри.

Граф сам по собі не відновлює стан. Для MVP потрібні відтворюваний reset, визначені fixtures та seed, якщо гра дозволяє його контролювати. Якщо replay розійшовся з очікуваним станом, записати розходження та переоцінити шлях.

## 11. Етапи реалізації та критерії готовності

### Етап 0 — перевірка середовища та рішення щодо інтеграції

Прочитати AGENTS.md, структуру Unity-проєкту, версію Editor, UI-технологію та наявні тести. Перевірити Unity CLI/Pipeline і Ollaya. Обрати наявну мову/стек для локального Host; якщо немає обмежень, C#/.NET є природним кандидатом для роботи в Rider. Зафіксувати рішення, не створювати одночасно кілька Host-реалізацій.

Готово: визначено реальний сценарій, спосіб reset, oracle, підтримувані дії, сумісність залежностей і фактичний протокол Ollaya.

### Етап 1 — контракти та Unity Runtime Core

Описати DTO, збір UI, provider контексту, registry і каталог дій. Отримати знімок у Play Mode без підключення моделі.

Готово: доступні елементи та дії відповідають тестовій сцені; неактивні елементи не стають виконуваними кандидатами; ID однозначні.

### Етап 2 — виконання, readiness та reset

Додати Direct Executor для мінімального набору контролів, результати команд, сесію, reset та очікування готовності.

Готово: вручну обраний actionId виконується; застарілі/невідомі дії відхиляються; повторний commandId не повторює ефект; після переходу отримується коректний стан.

### Етап 3 — CLI Adapter і наскрізний Runner

Підключити власні Editor-команди до Runtime Core. Реалізувати Game Connection, тайм-аути, журнал і ліміти Runner. Пройти сценарій за фіксованою послідовністю дій.

Готово: зовнішній процес керує сценарієм через CLI, визначає результат за oracle та зберігає trace. Runtime-збірка не залежить від Editor/Pipeline.

### Етап 4 — Ollaya Policy

Реалізувати перевірений локальний протокол, компактний контекст, кандидатів та обмежену історію. Замінити фіксовану послідовність вибором моделі.

Готово: Ollaya обирає тільки валідні actionId; некоректні відповіді й недоступність мають зрозумілий результат; є завершені наскрізні запуски без LLM-планувальника.

### Етап 5 — граф і перевірка заміни Policy

Додати State Identity Provider, Transition Recorder, просту Random Policy та Graph Exploration Policy з обмеженим пошуком/replay.

Готово: той самий Runner і Unity-пакет працюють із Ollaya та Graph Policy без змін контрактів; граф не розростається через таймери; повторний шлях перевіряється за фактичним станом.

### Етап 6 — стабілізація та документація

Повторити сценарій з однаковими fixtures, зберегти результати та описати запуск із Rider/термінала. Перевірити втрату Play Mode, timeout і недоступність Ollaya.

Готово: новий розробник може запустити сценарій за інструкцією, отримати pass/fail/інший явний результат і знайти причину невдачі у trace.

## 12. Перевірка якості

Автоматизовані перевірки зосередити на важливих межах: серіалізація контрактів, валідація відповіді моделі, дедуплікація команд, stale revision, state identity та поведінка Runner при timeout. Реальні Unity-переходи перевіряти у Play Mode на компактному сценарії.

Фіксувати на запуск: Policy, модель/конфігурацію, seed/fixtures, результат oracle, кількість кроків, повторів, станів/переходів і тривалість. Порівнювати Policy на однакових початкових умовах. Не трактувати один успішний прохід як доказ універсальності.

## 13. Розширення після MVP

1. Runtime Network Adapter для development-білдів; гра може ініціювати вихідне підключення до Host.
2. Input Executor для симуляції вводу та окремого вимірювання UI-доступності.
3. Інші UI/gameplay Interaction Providers.
4. Planner Policy: планувальник формує підціль, селектор обирає конкретну дію.
5. Збереження checkpoints, складніший replay, візуальні спостереження.

Мережевий адаптер має узгоджувати версію протоколу, ідентифікувати сесію та обмежувати доступ до тестових команд. Тестовий endpoint не вмикається автоматично у production-білді. Хмарні ключі моделі, якщо з'являться, належать Host, а не клієнту гри.

## 14. Вказівки для Codex, який імплементуватиме план

- Спочатку оглянути репозиторій і виконати Етап 0. Не припускати структуру проєкту, версії пакетів або протокол Ollaya.
- Використовувати наявні conventions, asmdef і підхід до тестування.
- Реалізовувати послідовно невеликими завершеними етапами з перевірюваними результатами.
- Не починати з універсального framework для всіх жанрів та UI-систем.
- Не додавати LLM-планувальник, хмарний Host або vision у першу ітерацію.
- Не змінювати глобальну інсталяцію Ollaya без необхідності; вона вже працює.
- Не змішувати внутрішні DTO з офіційним API моделі.
- Не використовувати довільне виконання згенерованого моделлю коду як механізм дій.
- Якщо гіпотеза про API чи можливості інструмента не підтвердилася, описати факт і скоригувати відповідний адаптер, зберігши спільні контракти.
- Після кожного етапу коротко повідомляти: що працює, як перевірено, які обмеження залишилися.
