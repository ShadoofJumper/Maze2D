# План першої ітерації Unity Runtime Core

Дата: 2026-11-17. Статус: перша реалізація створена; результати перевірок і запуск описані в README.md поруч із цим планом. Повний Player build залишається окремою перевіркою.

Основний документ: [UNITY_GAME_TEST_AGENT_PLAN.md](UNITY_GAME_TEST_AGENT_PLAN.md).

## 1. Мета та межі

Реалізувати Observer, Executor та Game Adapter із окремим Session Controller. Отримати структурований стан у Play Mode, вручну обрати запропонований actionId, виконати його та отримати наступний стан. Архітектура має дозволяти додати Editor/CLI або мережевий адаптер без зміни цих операцій.

Unity відповідає за спостереження, перевірку актуальності команд і виконання. Вибір дій, Runner, модель, граф переходів та збереження trace належать зовнішньому Host і не входять у цю ітерацію. Симуляція вводу також відкладається; перший режим виконання — Direct.

## 2. Відомі умови проєкту

### Підхід до описів і контексту

Базова робота має обходитися без QAContext-компонентів і без ручного опису кожного попапа або кнопки. Універсальний UGUI provider автоматично виявляє стандартні контроли та дії. Окремі MonoBehaviour-дескриптори — необов'язкове доповнення. Drag and drop не реалізується в цій ітерації.

Для першого запуску з AI людина готує один загальний опис гри в Assets/AutoQA/Config/GAME_DESCRIPTION.md: правила, основні взаємодії та значення важливих ігрових понять. Це звичайний текстовий файл, без ScriptableObject. Майбутній Host завантажує його за налаштованим шляхом і передає Policy окремо від цілі тесту. Runtime Core не читає цей файл і не додає його повторно до кожного observation. У поточній ітерації готуємо опис; його доставку моделі реалізуємо разом із Host.

У пакеті передбачити QAContext MonoBehaviour: Description у багаторядковому полі та необов'язковий SemanticKey. Розміщення — Runtime/Core/Context/. Компонент застосовується до екрана, попапа, контролу або об'єкта сцени; окремі класи для кожного виду кнопки не потрібні. Збір повертає структуровані записи з текстом, session-scoped ID власника та прив'язкою до UI-елемента, якщо вона є. Описи сцени й контейнерів зберігаються як окремі записи зі зв'язками, а не копіюються в кожну дочірню кнопку.

Враховувати активність об'єкта та видимість UI; для нестандартного приховування дати можливість провайдеру уточнити актуальність. Порожній список описів допустимий і не означає unavailable. Компоненти не додають обов'язкових умов для реєстрації стандартних дій.

Game Adapter повертає динамічні факти, readiness, fixtures та oracle незалежно від наявності текстових описів. Перша ітерація не вимагає від розробника писати описи екранів у C#.

Майбутній planner, який аналізує код проєкту, є окремою можливою функцією Host. Його API та доступ до коду зараз не реалізуються.

- Unity 6000.3.10f1; встановлені uGUI, Unity Test Framework та Unity Pipeline.
- MainMenuScreen має кнопки Play та Exit; Play відкриває LobbyScreen.
- LobbyScreen має кнопки і TMP_InputField для висоти, ширини та кількості виходів лабіринту.
- Гра використовує Zenject; частина бібліотек має asmdef, ігровий код переважно належить стандартній збірці.
- Перший сценарій: Main Menu → Lobby → встановлення валідних параметрів → Play → підтвердження готового gameplay.
- Перед реалізацією уточнити порядок ініціалізації сцени, UI-анімацій, gameplay та доступ до їхніх станів. Наявність класів сама по собі не підтверджує runtime readiness.

## 3. Розміщення та залежності

Відразу створити embedded UPM package. Ім'я com.maze2d.autoqa — початковий ідентифікатор пакета; публічний namespace — AutoQA.

```text
Packages/com.maze2d.autoqa/
  package.json
  Runtime/
    Core/
      Contracts/
      Sessions/
      Targets/
      Observations/
      Actions/
      Integration/
      AutoQA.Core.asmdef
    Integrations/UGUI/
      AutoQA.UGUI.asmdef
  Tests/
    EditMode/
    PlayMode/
  Documentation~/

Assets/AutoQA/
  GameIntegration/Runtime/
    Bootstrap/
    Providers/
    Scenarios/
  Config/
```

Core не залежить від гри, Zenject, UniRx, UnityEditor, Pipeline чи моделі. UGUI залежить від Core та потрібних UI-збірок. Ігрова інтеграція залежить від Core, UGUI і сервісів Maze2D. Bootstrap із Zenject залишається в Assets.

Ігровій інтеграції спочатку не додавати asmdef, якщо вона звертається до Assembly-CSharp. Не переносити весь ігровий код у нові assemblies лише заради AutoQA. Для тестових assemblies додати власні asmdef і перевірити доступність тестів embedded package через налаштування Test Framework. Порожні Editor-модулі й транспортні адаптери поки не створювати.

## 4. Склад і відповідальність

### Session Controller — Core

- Володіє lifecycle тестового підключення: початок, завершення, поточний sessionId.
- На новій сесії очищає target registry, каталог, revision та результати команд.
- Сесія переживає звичайний перехід сцени через persistent bootstrap; зупинка Play Mode або domain reload інвалідує її.
- Не ототожнюється з наявним GameSessionService: той керує ігровою партією.
- Reset гри є окремою операцією Game Adapter. Для першої ітерації відтворюваний старт допускається через повторний запуск Play Mode з початкової сцени; runtime reset не є критерієм готовності.
- Перевірити очищення також із вимкненим domain reload, щоб статичні посилання не переносили стару сесію.

### Observer — Core та UGUI

- Core об'єднує дані Interaction Provider і Game Adapter в один observation на головному потоці.
- UGUI provider виявляє Button і TMP_InputField у завантажених сценах, читає labels, values, active/interactable та причини недоступності.
- Знімок містить scene, screen, readiness, UI, gameContext, результати перевірок і конкретні availableActions.
- Не серіалізує довільні компоненти або всю сцену через reflection. Розширення gameplay-спостережень додаються провайдерами.
- Target Registry зберігає session-scoped ID → живий об'єкт. ID не перевикористовуються в межах сесії; знищені об'єкти видаляються. InstanceID може бути внутрішньою деталлю, але не міжсесійним locator.
- Action Catalog зберігає параметри кандидатів і відповідні handlers. Наприклад, setValue для поля містить уже підготовлене значення.
- Ігровий provider може надавати semantic keys і fixtures; semantic keys не потрібні для автоматичного виявлення або виконання стандартних дій. Якщо заданий key неоднозначний, повертати діагностику, а не вибирати довільну ціль.

### Executor — Core та UGUI

- Приймає commandId, sessionId, observationId/revision, actionId, execution mode і timeout.
- Перевіряє активну сесію, актуальність observation, існування кандидата, readiness та живу доступну ціль.
- Параметри бере із каталогу; команда не дозволяє передати довільний метод або нове значення.
- Дозволяє одну mutating command одночасно. Повтор того самого commandId повертає поточний або фінальний результат; інший payload із тим самим ID відхиляється.
- Результати зберігає протягом сесії. Надає операцію запиту статусу команди.
- UGUI handlers реалізують натискання Button і встановлення TMP_InputField з узгодженою семантикою подій. Перевірити її на реальних callbacks гри.
- Direct перевіряє active/interactable та застосовні UI-обмеження. Не гарантує фізичну досяжність чи відсутність перекриття; execution mode присутній у результаті.
- completed означає виконану операцію. Перехід сцени й успіх сценарію перевіряються наступним observation.
- Timeout не означає скасування вже виконаного ефекту. Для синхронних Unity callbacks немає безпечного примусового переривання; не обіцяти його контрактом.

### Game Adapter — контракти в Core, реалізація в Assets

Використати невеликі контракти провайдерів контексту, готовності, fixtures та перевірок. Game Adapter є точкою їх композиції, а не одним великим інтерфейсом з усіма майбутніми можливостями.

Maze2D-реалізація:

- Надає screen/state та значущі параметри лабіринту через явні API гри.
- Надає readiness на основі завершення ініціалізації/переходів; відсутність UI-кнопок не є readiness-сигналом.
- Визначає валідні fixtures для трьох полів за обмеженнями гри.
- Зіставляє semantic keys із потрібними UI-цілями; виключає Exit із кандидатів стартового сценарію.
- Перевіряє, що gameplay ініціалізований і застосовано очікувані параметри. Самої назви сцени недостатньо для успіху.
- Якщо потрібного публічного сигналу немає, додає мінімальний read-only API або подію до гри, без залежності ігрових сервісів від AutoQA.

## 5. Узгодженість observation і команд

- Observation DTO відокремлені від UnityEngine.Object; мають schemaVersion та JSON-представлення.
- Повторне читання незміненого стану зберігає observationId/revision. Окремий captureId можна використати для діагностики.
- Revision змінюється при зміні сцени, screen, readiness, значущих UI-даних, контексту або кандидатів. Таймери та інші суто діагностичні значення не повинні інвалідувати команди.
- Для першої версії використовувати детерміноване порівняння нормалізованої проєкції цих даних, включно з доступністю та параметрами дій. Це механізм актуальності, а не state identity для майбутнього графа.
- Перед виконанням повторно оновити проєкцію і перевірити revision та передумови. Реєстр і каталог публікувати узгоджено зі знімком.
- Після початку mutating command інвалідувати попередні кандидати; новий набір публікується наступним capture. Це не дозволяє виконати другу стару дію, навіть якщо візуально стан не змінився.
- Помилки провайдерів не повинні породжувати вигаданий ready-стан: повертати діагностику та unavailable для критично неповного observation.

## 6. Послідовність імплементації

### Крок 1 — пакет і контракти

Створити package.json, Core/UGUI assemblies, DTO, контракти провайдерів і runtime facade: BeginSession, EndSession, CaptureObservation, Execute, GetCommandStatus. Узгодити JSON-серіалізатор за фактичними залежностями проєкту; gameContext має підтримувати документовані JSON-сумісні дані. Назви API попередні.

Готово: пакет компілюється; контракти проходять JSON round-trip; Core не має Editor або ігрових залежностей.

### Крок 2 — сесія, registry та каталог

Реалізувати lifecycle, унікальні ID, очищення та збереження команд. Визначити ownership і Dispose для підписок та persistent bootstrap.

Готово: нова сесія відхиляє старі ID; знищений target недоступний; перехід сцени не створює другого controller.

### Крок 3 — Observer та UGUI provider

Реалізувати capture, проєкцію актуальності, каталог дій і providers для Button/TMP_InputField. Додати компактну тестову сцену пакета.

Додати необов'язковий QAContext і збір його описів. Основна тестова сцена/сценарій працює без дескрипторів; окремий тест перевіряє прив'язку опису екрана та контролу, а також виключення прихованого контексту.

Готово: активні елементи й кандидати відповідають сцені; недоступні елементи не породжують дій; повторне читання стабільне; релевантна зміна оновлює revision.

### Крок 4 — Executor

Реалізувати валідацію, Direct handlers, результати, дедуплікацію та перевірку стану безпосередньо перед дією.

Готово: вручну обрані кандидати виконуються; неправильна сесія, stale revision, невідомий actionId і недоступний target відхиляються; повтор commandId не повторює callback.

### Крок 5 — Maze2D Game Adapter

Підключити через bootstrap провайдери контексту, readiness, fixtures, semantic keys і oracle першого сценарію. Зберегти конфігурацію гри в Assets/AutoQA/Config.

Підготувати один GAME_DESCRIPTION.md. Не розмічати Main Menu, Lobby та їхні кнопки QAContext-компонентами для проходження базового сценарію. Semantic keys тестового harness можна надати через Game Adapter без компонентів на кожному об'єкті.

Готово: observation відрізняє Main Menu, Lobby, перехід і готовий gameplay; запропоновані значення валідні; oracle підтверджує застосовані параметри.

### Крок 6 — наскрізна перевірка без моделі

Створити Play Mode test/harness, який викликає runtime facade напряму. Після кожного кроку отримує новий observation, обирає кандидата за semantic key та очікує явну readiness з timeout. Не хардкодити runtime ID.

Готово: Main Menu → Lobby → заповнення параметрів → Play → oracle проходить; помилки та тайм-аути дають явну причину. Документація описує запуск і межі Direct mode.

Ця перевірка підтверджує роботу Runtime без дескрипторів, але не здатність моделі зрозуміти гру. На етапі підключення Policy окремо перевірити вибір дій за одним загальним описом та автоматичними observation без локальних текстових підказок.

## 7. Перевірки

Edit Mode: JSON round-trip; lifecycle; ID та cleanup; незмінний/змінений observation; stale revision; невідомі кандидати; дедуплікація й конфлікт payload; обробка exceptions провайдерів/handlers.

Play Mode: реальні Button/TMP_InputField callbacks; disabled/знищені цілі; зміна стану між capture та execute; зміна сцени; повторний Play Mode; наскрізний сценарій Maze2D. Перевірити компіляцію Runtime для Player без Editor/Pipeline-залежностей.

Ігрові дефекти, виявлені під час сценарію, фіксувати окремо. Наприклад, у LobbyScreen.OnHide зараз додається OnPlay listener замість видалення — це може дублювати запуск; повторний callback гри слід відрізняти від повторного виконання команди AutoQA.

## 8. Результат першої ітерації

Переносимий Unity-пакет із Observer, Executor, Session Controller і контрактами інтеграції; окремий Maze2D adapter; перевірений сценарій без моделі та транспорту. Наступний етап підключає Editor/CLI adapter до існуючого runtime facade.
